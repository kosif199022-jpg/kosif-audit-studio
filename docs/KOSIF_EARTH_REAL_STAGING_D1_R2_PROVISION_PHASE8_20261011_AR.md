# KOSIF EARTH — المرحلة الثامنة: تجهيز موارد Staging حقيقية ومعزولة

**التاريخ:** 11 أكتوبر 2026 · **خادم المراجعة:** `kosif199022-jpg/kosif-audit-studio`، فرع `chatgpt/kosif-earth-server-tenant-guard-20261010`، Draft PR #42 · **لا إنتاج ولا نشر Worker**.

## الموارد المنشأة في Cloudflare فعلًا

تم الاتصال بحساب Cloudflare المرتبط بمستودع الخادم واستخدام واجهة Cloudflare API لإنشاء موردين **جديدين وفارغين** بعد التأكد من عدم وجودهما سابقًا:

| المورد | الاسم | بيانات الربط |
|---|---|---|
| قاعدة D1 اختبارية فقط | `kosif-audit-tenant-staging-20261011` | `KOSIF_DB`، UUID `2bf580c6-6a80-41bb-a59c-f96a6b4d3c0f` |
| حاوية R2 اختبارية فقط | `kosif-audit-tenant-staging-docs-20261011` | `KOSIF_DOCUMENTS`، اسم الحاوية مستقل عن الموجود |

لم تتغير قواعد أو حاويات `SEE` أو `kosif_db` القديمة، ولم يجرِ تنفيذ استعلام على بياناتها.

## تهيئة منفصلة وليست تصريح نشر

أُضيف الملف `cloudflare/wrangler.staging.toml` مع اسم Worker اختباري مستقل `kosif-audit-tenant-staging-20261011`، وربط D1 وR2 بتعريفين صريحين، و`KOSIF_TENANCY_MODE=strict`، وOrigin معروف محدد دون wildcard، مع `workers_dev=false`.

لم يُضف أي `KOSIF_AUTH_JWT_SECRET` أو `KOSIF_BACKUP_HMAC_SECRET` أو هوية مدير داخل الملف. **لم يتم اختراع issuer أو وضع secret في Git**. لذلك `KOSIF_AUTH_ISSUER` **غير معرف عمدًا**، وتعيد `scripts/tenant-staging-release-gate.mjs` الآن `readyForOfflineReview:false`، و`liveDeploymentAuthorized:false`، وexit code **2** مع مانع إعداد واحد متبقٍ: `kosif_auth_issuer_unconfigured`. تبقى شروط تحقق خادم JWT الحي والمرفقات والتوقيع والمراجعين المستقلين غير مثبتة، حتى بعد إضافة issuer.

## اختبار القاعدة الحقيقية (وليس محاكاة)

- قبل الهجرة لم تحتوِ D1 الجديدة سوى جدول Cloudflare الداخلي.
- طُبقت مخططات المشروع `0001_v5_document_intelligence.sql` و`0002_v5_engagement_persistence.sql` و`0003_verified_company_ownership.sql` باستخدام **12 عبارة CREATE TABLE/INDEX** على D1 الاختبارية الجديدة فقط. التحقق اللاحق كشف **7 جداول و5 فهارس** مطابقة لجدول العمل.
- أُضيفت مؤقتًا **أربعة سجلات اصطناعية**: ملف مراجعة وملكيته للشركة A، وملف مراجعة وملكيته للشركة B. الاستعلامات التي تقيد `company_id/workspace_id` أعادت `a_self=1,b_self=1,b_reads_a=0,a_reads_b=0`.
- بعد ذلك حُذفت السجلات الأربعة وتم التأكد أن `engagements=0, engagement_ownership=0, documents=0`.
- هذه **تجربة مخطط واستعلام حقيقية على Cloudflare D1**، وليست إثبات مصادقة HTTP أو فرض تفويض JWT بواسطة Worker.

## اختبار حاوية R2 الحقيقية

رفعنا ملف نص صغير لا يحتوي بيانات مستخدم إلى الحاوية الجديدة بمفتاح `synthetic-stage-check-20261011.txt`، ثم أُجري GET ناجح (200) وحذف ناجح (200). فحص قائمة الحاوية بعد الحذف أعاد **0 ملفات**. هذه تجربة R2 تخزين فعلية، لكنها ليست اختبار R2 عبر JWT أو بوابة تنزيل مستندات التطبيق.

## حالة اختبار الكود

- إضافة اختبار جديد إلى `tests/tenant-staging-release-gate.test.js` يتأكد من الأسماء والتعريفات الصريحة وعدم تسرّب أسرار إلى ملف الإعداد، وأنه يفشل عمدًا دون issuer.
- يُلحق إحصاء `npm test` و`npm run check` في سجل التطوير بعد التحقق.
- لم يُنشأ Worker منشور أو حساب مستخدم أو جهة إصدار JWT، ولم تُطبق أي هجرة على الإنتاج، ولم يُكتب سند/طلب/مستند فعلي لشركة عميل.

## ما يلزم قبل الإطلاق الاختباري التالي

1. **مصدر JWT موثوق مستقل** يدعم متطلبات خادم `authenticatedScope()`: `HS256` مؤمن صادر من جهة منفصلة مع `issuer`, `audience`, `sub`, `companyId`, `workspaceId`, `iat`, `exp`. لا يجوز أن تنشئ الواجهة هذا الرمز بنفسها. الأفضل مستقبلًا مراجعة هوية تعتمد JWKS/توقيعًا غير متماثل لتجنب مشاركة مفتاح HMAC مع جهة إصدار خارجية.
2. تركيب أسرار staging **خادم-فقط** من لوحة Cloudflare أو CLI محلي دون إرسالها في المحادثة أو تسجيلها أو تضمينها في Git، وإنشاء حساب مراجع ومدير فعليين وعدم اختيار الهوية عشوائيًا.
3. اعتماد عنوان تطبيق تجربة منفصل قبل تفعيل الـOrigin، ثم فحص إصدار التوكن وربط شركة A/B والصلاحيات والـD1/R2 عبر HTTP من خلال Worker منشور في بيئة تجربة فقط.
4. اختبار `GET/PUT` والحفظ المتزامن ومرفقات R2 والنطاق الأجنبي، ونسخة HMAC منتهية أو معدلة، وعدم تغيير D1 عند الرفض، وعودة الخطأ دون تسريب.
5. الاستعادة الفعلية لشركة كاملة لا تزال **مقفولة**؛ تتطلب ملكية دقيقة لدفاتر المحاسبة والمخزون والمشتريات والمرفقات، وموافقَتين بشريتين، وprepare/approve/commit/rollback مع التحقق من السجلات.

**مهم:** تجهيز الموارد وتشغيل استعلامات اصطناعية لا يساوي تشغيل الـWorker أو إثبات حدود الصلاحيات. PR #42 يبقى Draft، وPR #247 يبقى Draft.
