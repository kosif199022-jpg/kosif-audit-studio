## اختبارات فعلية داخل D1 — شركتان وهميتان A وB

استخدمنا REST API الإداري لقاعدة Staging المعزولة فقط، مع أسماء حقلية اصطناعية `stg-company-A/B`، `stg-workspace-A/B` وملفات مراجعة `stg-proof-A/B-20261011`.

1. إدخال سجلي ملفين وإنشاء سجل الملكية المستقل لكل شركة نجح.
2. استعلامات `JOIN engagement_ownership` مع **companyId + workspaceId + ownerSubject** أعادت ملف الشركة نفسها فقط.
3. عند تمرير subject الخاص بـB مع Company A أو workspace من B مع Company A، أعاد الاستعلام صفر صفوف.
4. حُذفت جميع سجلات A/B الاختبارية من D1. تحققنا بعد الحذف أن `engagements=0` و`engagement_ownership=0` و`documents=0` في القاعدة الاختبارية.

**حدود الدليل:** REST API الإداري يمتلك صلاحيات أعلى من المستخدم، ولذلك هذه اختبارات تهيئة SQL ومؤشرات ملكية على قاعدة حقيقية، **ولا تمثل اختبار HTTP للـWorker، أو JWT، أو RBAC حي**.

## تجربة R2 الفعلية

- رفع ملفين اصطناعيين `staging-proof/A/canary-20261011.json` و`staging-proof/B/canary-20261011.json` إلى حاوية Staging وحدها؛ نجح `PUT` لكل ملف.
- استخدمنا `GET /objects?prefix=` لكل شركة؛ أظهر كل استعلام مفتاح الشركة الاختباري وحده.
- نجح حذف `DELETE` للملفين، وأكدت إعادة الفحص أن `staging-proof/` فارغ.
- **تنبيه:** هذا فصل أسماء مفاتيح في API الإدارة، وليس إثبات عزل بواسطة Worker مُصدر JWT؛ حساب Cloudflare الإداري يستطيع قراءة كلا المسارين.

## خلل إضافي اكتُشف وأُصلح في كود المستندات

كانت واجهة رفع المستندات تقبل `documentId` من العميل وتكتب `INSERT OR REPLACE INTO documents`، بينما `documents.id` مفتاح أساسي عالمي. عند تكرار معرّف مستند من ملف مراجعة آخر، قد تُعاد نسبة السجل لملف مختلف.

1. `cloudflare/gateway-worker.js`: يتحقق قبل رفع R2 أو التحليل من ملكية أي `documentId` متاح بالفعل في D1؛ يرفض المستند الأجنبي بـ`409 document_id_not_available` حتى إذا كان Bearer ملف A صحيحًا.
2. `cloudflare/document-worker.js`: استبدل `INSERT OR REPLACE` بعملية UPSERT مشروطة على `documents.engagement_id=excluded.engagement_id`. تحمي D1 نفسها ضد السباق بين الفحص والحفظ.
3. الاستجابة لا تصرح `ok:true` إذا فشل حفظ D1؛ تُرجع 409 لتعارض المعرّف أو 503 لتعذر الحفظ. لا تبدأ مرحلة التحليل بعد فشل الحفظ.
4. `tests/document-id-tenant-collision.test.js`: خمس حالات تشمل Bearer صحيح مع معرّف B، وتحديث معرّف المالك الصحيح، وسباق `changes=0`، وتعطل D1، ورفض Bearer خاطئ؛ نجحت **5/5**.

### اختبار إضافي على D1 الحقيقية

إدخال ملفين وهميين A/B ومستند عالمي واحد مملوك لـB:
- إدخال مستند B: `changes=1`.
- محاولة UPSERT بنفس المعرّف تحت ملف A: `changes=0`، والتحقق اللاحق أثبت بقاء `engagement_id=B` والاسم الأصلي كما هو.
- تحديث B لمستندها نفسه: `changes=1`.
- حذف المستند والملفين الاصطناعيين: نجح، دون بقاء بيانات اختبارية.

## موانع P0 المتبقية

1. **المُصدر الحقيقي للهوية:** لم تُوفّر هوية `KOSIF_AUTH_ISSUER` موثوقة أو مفاتيح JWT/HMAC من الجهة المصرح لها، ولم نكتب أسرارًا في Git.
2. **الـWorker على Staging:** لم يُنشر ولم نختبر طلبات A/B HTTP عبره، لذا لا يوجد إثبات حي لعزل المرفقات أو الاعتماد البشري.
3. **معاملة D1/R2 عبر شبكتين:** قد يظل ملف R2 يتيمًا إذا نجح `put` وفشل D1 لاحقًا؛ يلزم استراتيجـية حجز IDs وتراجع أو تنظيف آمن قبل الإنتاج. كذلك لا يثبت مفتاح R2 وحده ملكية الشركة.
4. **استعادة الشركة الكاملة:** ليست جاهزة؛ تصدير EARTH المحلي `restorable:false`، وتحتاج الحسابات والمخزون والمشتريات وملفات المراجعة لترحيل ملكية وتوقيع وتفويض وrollback من خادم حقيقي.
5. **الإصدار والاعتماد البشريان:** صلاحيات مستخدمين مستقلين وتدقيق الموافقات قبل إصدار تقارير أو استعادة لم تُنفذ بعد.
